SHOPGRAPH — ADD PARALLEL LOCAL OLLAMA RECEIPT ACQUISITION PIPELINE
==========================================================

TASK
----

Analyze the attached/current ShopGraph codebase and add a NEW AI-based receipt
acquisition capability without removing, replacing, or breaking the existing OCR
Acquisition Pipeline.

The goal is to create a parallel path that can use an local Ollama vision model to read a
receipt image and produce the SAME downstream-compatible kind of raw receipt
output expected by the existing Data Base Builder.

The existing OCR path must remain fully usable.

This version must use OLLAMA ONLY for the new intelligent receipt-acquisition
capability. It must run locally and must not require OpenAI or any other paid/cloud
AI API.

The new Ollama path should integrate into ShopGraph's current architecture rather than
creating a separate application or redesigning unrelated systems.


==========================================================
CURRENT ARCHITECTURE TO PRESERVE
==========================================================

ShopGraph currently has an existing capability:

    1. OCR Acquisition Pipeline

and related modes such as:

    OCR Acquisition Pipeline - All Images
    OCR Acquisition Pipeline + Data Base Builder
    OCR Acquisition Pipeline - All Images + Data Base Builder

Pipeline Part 1 currently performs approximately:

    1. Clean Generated Processing Data
    2. Clean Current Receipt Images
    3. Import Picture
    4. Update Purchase History Copy
    5. OCR Acquisition Pipeline + Data Base Builder
    6. Pipeline Export 1

The existing Pipeline Part 1 implementation obtains raw OCR output from:

    run_ocr_acquisition_pipeline_for_image(...)

and then passes the resulting raw OCR file(s) to the existing Data Base Builder
through the current receipt-import workflow.

DO NOT remove or alter the old OCR path merely because the new Ollama path exists.


==========================================================
PRIMARY GOAL
==========================================================

Add a new parallel capability named:

    Ollama Receipt Acquisition Pipeline

Conceptually:

    Receipt Image
        ↓
    Local Ollama Vision Receipt Analysis
        ↓
    ShopGraph-compatible Raw Receipt JSON
        ↓
    Existing Data Base Builder
        ↓
    Existing Purchase History / benchmark / taxonomy workflow

The most important architectural rule is:

    THE NEW Ollama PIPELINE MUST HAND OFF TO THE EXISTING SHOPGRAPH DOWNSTREAM
    FRAMEWORK THROUGH A CLEAR COMPATIBILITY BOUNDARY.

Do not rewrite the Data Base Builder around a completely different Ollama schema if
that can reasonably be avoided.

Prefer adapting the Ollama result into the same or a deliberately compatible raw
receipt representation already consumed by ShopGraph.


==========================================================
KEEP BOTH ACQUISITION ENGINES
==========================================================

After this update ShopGraph should have TWO independent receipt acquisition
engines:

    A. OCR Acquisition Pipeline
       - existing implementation
       - Tesseract / image variants / OCR comparison / reconstruction
       - unchanged and still selectable

    B. Ollama Receipt Acquisition Pipeline
       - new implementation
       - sends the selected receipt image to an local Ollama vision model
       - asks the model to transcribe the receipt conservatively
       - converts the result to ShopGraph-compatible raw receipt data

The user must be able to choose either path.

Do not silently replace the existing OCR implementation.

==========================================================
OLLAMA LOCAL MODEL / CONFIGURATION
==========================================================

This implementation must use OLLAMA ONLY.

Do NOT integrate cloud AI provider, Anthropic, Google Gemini, a paid cloud inference API,
or any other hosted AI provider.

Do NOT require an Ollama service/model, cloud account, token billing, or per-receipt AI fee.

The intended architecture is:

    ShopGraph
        ↓
    Ollama running locally on the user's computer
        ↓
    Local vision-capable model
        ↓
    Receipt transcription returned to ShopGraph

Communicate with Ollama through its local HTTP API, normally:

    http://localhost:11434

Keep the Ollama base URL configurable in one obvious location, with localhost as
the default.

Use Ollama's documented local API for image-capable/chat generation. The image
must be supplied in the format expected by the local Ollama API.

Do not require the Python `ollama` package unless it provides a compelling
advantage. Prefer Python's standard-library HTTP facilities if that keeps the
project simpler and avoids a new dependency.

The implementation must perform controlled availability checks.

If Ollama is not installed or the local Ollama service cannot be reached:

    - print a clear message explaining that Ollama must be installed and running;
    - do not show an opaque traceback;
    - do not modify Purchase History;
    - leave the existing OCR pipeline fully usable.

If the configured vision model is not installed locally:

    - identify the missing model clearly;
    - tell the user the exact `ollama pull <model>` command needed;
    - do not automatically download a large model without user approval;
    - do not modify Purchase History.

MODEL CONFIGURATION
-------------------

Keep the Ollama model name configurable in ONE obvious location.

Use an environment variable such as:

    SHOPGRAPH_OLLAMA_MODEL

and/or ShopGraph's existing non-secret settings architecture.

There is NO Ollama service/model.

Choose a sensible vision-capable default model supported by Ollama, but isolate
that choice behind a constant/configuration value so it can be changed later
without changing pipeline logic.

Do not scatter model names throughout the project.

Also support a configurable base URL such as:

    SHOPGRAPH_OLLAMA_BASE_URL

with default:

    http://localhost:11434

LOCAL-ONLY REQUIREMENT
----------------------

For this capability, receipt images and prompts must be sent only to the locally
running Ollama service.

Do not silently fall back to cloud AI provider or another cloud provider.

Do not add telemetry or upload receipt images elsewhere.

The existing non-AI OCR path remains available as a completely separate fallback
that the USER may choose manually.

==========================================================
OLLAMA MODEL'S JOB
==========================================================

The local Ollama vision model is replacing RECEIPT OCR / TRANSCRIPTION, not the rest of
ShopGraph.

The Ollama should inspect the receipt image and reconstruct the receipt faithfully.

It should identify the printed receipt content in top-to-bottom order.

Preserve receipt evidence rather than prematurely converting the receipt into the
final Purchase History taxonomy.

The Ollama acquisition layer should focus on things such as:

    - line order
    - printed text
    - product descriptions
    - SKU / PLU / item codes when visible
    - tax codes when visible
    - monetary values
    - promotion/reference-price lines
    - savings lines
    - quantity/weight/pricing-detail lines
    - subtotal/tax/total lines
    - store/date/store-number evidence when visible

Do NOT ask the Ollama acquisition layer to invent:

    Common Name
    Sub-Category
    broad Category

Those belong to later ShopGraph stages.


==========================================================
CONSERVATIVE TRANSCRIPTION RULES
==========================================================

The Ollama receipt prompt should explicitly require conservative behavior.

Rules should include:

1. Preserve receipt line order.

2. Do not invent text that cannot reasonably be read.

3. If text is genuinely unreadable, represent uncertainty explicitly rather than
   fabricating a confident value.

4. Do not collapse repeated products merely because the text is identical.

5. Do not treat a promotional/reference amount as automatically being the final
   item charge.

6. Preserve savings lines such as:

       You saved: $0.62

   as receipt evidence rather than turning them into product purchases.

7. Preserve pricing-detail lines such as:

       1 @ 10 for $10.00    1.00

   so downstream ShopGraph logic can distinguish promotional/reference amounts
   from final charges.

8. Preserve zero-price purchases when the receipt actually shows 0.00.

9. Preserve quantity and weighted-item evidence.

10. Preserve subtotal/tax/total/payment metadata rather than misclassifying it as
    product text.

11. Preserve repeated independently purchased items separately.

12. Do not infer a six-digit SKU merely because some unrelated six-digit number
    appears in receipt metadata.

13. Output only evidence supported by the image.

==========================================================

Before implementing the new writer, inspect exactly what the current Data Base
Builder expects from raw OCR JSON.

Do NOT guess the schema.

Study the existing:

    capabilities/OCRAcquisitionPipeline/
    utils/DataBaseBuilder/receipt_loader.py
    utils/DataBaseBuilder/data_base_builder_main.py
    utils/DataBaseBuilder/receipt_item_interpreter.py
    store-specific parsers
    session-state / selected-raw-OCR behavior

Then define the smallest compatibility adapter necessary.

The Ollama-generated file should contain all fields required by the existing
downstream code.

If some OCR-specific metadata has no meaningful Ollama equivalent, populate it with a
safe compatible value rather than changing unrelated downstream systems merely to
satisfy an OCR-specific field.

Document every compatibility decision.

The Ollama-generated raw receipt output should remain inspectable by a human.
