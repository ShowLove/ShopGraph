SHOPGRAPH — NEW PURCHASE COMMON NAME + SUB-CATEGORY ANALYSIS
============================================================

TASK
----

Analyze the attached/exported ShopGraph file:

    data/database/shopgraph_purchase_history.txt

This file is a CSV-formatted export of the "Purchase History" worksheet.

Your job is to analyze the NEWLY ADDED purchase-history rows and assign the best:

    Common Name
    Sub-Category

to EVERY new row.

IMPORTANT:

The new rows may already contain Common Name and/or Sub-Category values.

DO NOT automatically preserve those values.

They are provisional data and should be independently reviewed along with every
other new row.

The OLDER historical rows are the authoritative taxonomy reference.

The NEW rows are the rows being classified.

============================================================
CORE DISTINCTION — HISTORICAL ROWS VS NEW ROWS
============================================================

Treat the database as two conceptual groups:

    HISTORICAL ROWS
        authoritative reference data

    NEW ROWS
        items that must be analyzed/reclassified

The user will identify the first new Excel row, for example:

    Analyze all items from row 125 down.

In that example:

    Rows 1-124
        = historical taxonomy/reference data

    Rows 125 through the final populated row
        = new items to classify

This distinction is extremely important.

============================================================
HISTORICAL TAXONOMY — PRESERVE IT
============================================================

Rows BEFORE the requested starting row are authoritative.

Use them to learn ShopGraph's:

    Common Name conventions
    Sub-Category taxonomy
    classification granularity
    product relationships
    retailer/SKU relationships

DO NOT propose changes to historical rows.

DO NOT:

    rename historical Common Names
    rename historical Sub-Categories
    merge historical Sub-Categories
    reorganize historical taxonomy
    normalize historical values
    "clean up" historical classifications

Historical assignments are evidence of the user's intended taxonomy.

============================================================
NEW ROWS — ANALYZE EVERY ITEM
============================================================

Analyze EVERY row from the requested starting row through the final populated
purchase-history row.

Do this regardless of whether its current Common Name or Sub-Category is:

    blank
    NA
    already populated

For every new row, independently determine the best:

    Common Name
    Sub-Category

The existing Common Name/Sub-Category values in NEW rows are useful evidence,
but they are NOT authoritative.

They may be:

    accepted unchanged
    refined
    replaced
    corrected

when analysis indicates another result better matches the established historical
ShopGraph taxonomy.

Example:

If a new row contains:

    Product:
        Org Baby Carrots

    Existing Common Name:
        NA

    Existing Sub-Category:
        Baby

but historical ShopGraph taxonomy shows fresh carrots and vegetables belong in:

    Fresh Vegetables

then classify the new row as:

    Organic Baby Carrots
    Fresh Vegetables

Do not preserve an obviously inappropriate provisional classification merely
because the field was already populated.

============================================================
ANALYZE THE NEW BLOCK AS A COHERENT BATCH
============================================================

Do not analyze only the blank cells.

Study ALL new rows together.

This allows populated new rows to provide evidence about:

    repeated products
    related products
    receipt patterns
    SKU patterns
    naming consistency

but do not allow an incorrect provisional classification in one new row to
override stronger historical taxonomy evidence.

When multiple new rows clearly represent related or identical products, classify
them consistently.

============================================================
HOW TO INFER COMMON NAME
============================================================

Use all relevant fields, especially:

    Store
    Six-Digit SKU
    Product
    Tax Code
    Store Number
    historical purchase records
    repeated product appearances
    related new rows

Common Name should describe the real-world product in a stable,
human-readable way rather than simply copying noisy receipt text.

Prefer an existing historical Common Name when the new row clearly represents
the same product.

Use SKU/store/product relationships when available.

A matching SKU from the same retailer is strong evidence, but do not force a
match when product evidence conflicts.

When creating a genuinely new Common Name:

- use a concise recognizable product name;
- remove receipt/OCR clutter;
- retain meaningful brand/product distinctions;
- retain useful size/variant information when appropriate;
- follow the naming style of historical ShopGraph data;
- do not invent unsupported product details.

============================================================
HOW TO INFER SUB-CATEGORY
============================================================

First study the complete set of HISTORICAL:

    Common Name -> Sub-Category

assignments.

For every new item:

1. Reuse an existing Sub-Category when it genuinely represents the same type
   of item.

2. Prefer consistency with established historical ShopGraph classifications
   over provisional classifications appearing in the new rows.

3. Prefer the established historical level of specificity.

4. Do NOT preserve an overly broad provisional new-row Sub-Category merely
   because it is populated.

For example, if historical ShopGraph distinguishes:

    Fresh Fruit
    Fresh Vegetables
    Frozen Vegetables
    Bread
    Specialty Cheese
    Baby Care

do not automatically retain new provisional categories such as:

    Produce
    Bakery
    Dairy
    Baby

when a more appropriate established Sub-Category applies.

5. Do NOT force an item into an existing Sub-Category merely because it is the
   closest existing category.

6. Create a NEW Sub-Category when the item represents a materially different
   product type that is not adequately represented by the historical taxonomy.

============================================================
NEW SUB-CATEGORIES
============================================================

ShopGraph's database may expand into completely new domains.

New purchases may include:

    groceries
    home improvement
    tools
    automotive
    electronics
    office supplies
    garden
    furniture
    pet supplies
    clothing
    services
    or anything else

Do not assume new purchases resemble the existing database.

When a genuinely new product type appears, create an appropriate new
Sub-Category.

A new Sub-Category should:

- be specific enough to remain analytically useful;
- be broad enough to contain future comparable products;
- match the naming style and granularity of established ShopGraph
  Sub-Categories;
- describe WHAT the item is;
- not describe the retailer;
- avoid generic catch-all labels when a useful product-type classification is
  possible.

Examples of reasonable new classifications might include:

    Cooking Oils & Sprays
    Canned Tomatoes
    Tortillas
    Frozen Sandwiches
    Snack Cakes

but create these only when supported by the actual new products and existing
taxonomy.

============================================================
CONSISTENCY CHECKS
============================================================

Before producing the answer:

1. Build an internal reference map of HISTORICAL:

       Common Name -> Sub-Category

2. Check whether each new product matches an existing historical Common Name.

3. Check retailer + SKU relationships where available.

4. Check whether the proposed Sub-Category already exists under the same
   concept.

5. Avoid creating near-duplicate Sub-Categories differing only by wording,
   capitalization, singular/plural, or minor phrasing.

6. Prefer established granular historical categories over unusually broad
   provisional categories appearing only in the new block.

7. If a genuinely new product domain is encountered, create the needed new
   Sub-Category rather than distorting an existing category.

8. Apply the same reasoning consistently across all new rows.

9. Review populated new-row classifications just as carefully as blank ones.

============================================================
UNCERTAINTY
============================================================

Make the best evidence-based classification when reasonable.

If a product is genuinely too ambiguous to identify or classify reliably from
the available information, use:

    NA

Do not fabricate a specific identity merely to avoid NA.

However, do not use NA simply because a product requires reasonable inference
from ordinary receipt abbreviations.

============================================================
OUTPUT FORMAT — IMPORTANT
============================================================

The goal is easy copy/paste into the actual Excel "Purchase History" worksheet.

The export's first CSV line corresponds to Excel row 1.

Therefore source line numbers correspond to Excel row numbers.

The user will specify a starting row.

Analyze:

    starting row -> final populated row

Return TWO sections only.

============================================================
SECTION 1 — COMPLETE NEW-ROW REVIEW TABLE
============================================================

Provide a Markdown table:

| Excel Row | Store | Product | New Common Name | New Sub-Category | Reason |
|---:|---|---|---|---|---|

IMPORTANT:

Include EVERY row from the requested starting row through the final populated
row.

Do NOT include only rows containing NA.

For each row, show the FINAL recommended:

    Common Name
    Sub-Category

even when the recommendation happens to be identical to the values already
present in the new row.

The Reason should briefly explain the classification.

When useful, indicate whether the decision:

    matches historical precedent
    corrects a provisional new-row classification
    creates a genuinely new Sub-Category

Keep Reason concise, usually one sentence.

============================================================
SECTION 2 — COMPLETE COPY/PASTE BLOCK
============================================================

Return replacement values for EVERY analyzed new row.

Because the entire new block has been independently reviewed, the output is
intended to replace columns:

    H = Common Name
    I = Sub-Category

for the entire requested new-row range.

For example, if the request is:

    Analyze all items from row 125 down

and the final row is 152, output:

    Paste into H125:I152

Then provide a TAB-SEPARATED code block containing exactly two columns:

    Common Name<TAB>Sub-Category

Rules:

- no header row;
- exactly two tab-separated values per row;
- Common Name first;
- Sub-Category second;
- exact Excel row order;
- exactly one output line for every analyzed Excel row;
- include populated and previously unpopulated new rows;
- do not omit a row because its existing values happened to be correct;
- output the FINAL recommended values;
- the number of lines in the paste block MUST exactly equal the number of
  analyzed new rows.

This allows the entire H:I range for the newly added purchase block to be
replaced safely in one paste operation.

============================================================
FINAL BEHAVIOR
============================================================

The key rule is:

    HISTORICAL DATA TEACHES THE TAXONOMY.
    NEW DATA IS COMPLETELY RECLASSIFIED.

Do not modify or recommend changes to historical rows before the requested
starting row.

Do independently analyze every row from the requested starting row onward.

Do not assume populated Common Name/Sub-Category fields in the new block are
correct.

Use them as evidence, not authority.

Return:

    1. Complete review table for ALL new rows.
    2. Complete H:I copy/paste block for ALL new rows.

Do not rewrite the complete Purchase History.

Do not return a replacement CSV.

Do not create a broad "Category" field.

Only produce Common Name and Sub-Category classifications for the requested
new-row block.
